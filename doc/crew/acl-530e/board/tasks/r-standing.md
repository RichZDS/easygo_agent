# R · 常驻终审

assignee: review · 状态: 常驻（每笔交付由工头发简令点名，简令里写明提交号与对应任务单）

## 现场 / 锚点
- 被审的提交在各施工者的分支上，本仓库共享对象库，可以直接 `git show <sha>`：
  - workshop 席：`feat/acl-workshop`
  - loop 席：`feat/acl-loop`
- 审查依据：
  - 施工图 `board/tasks/<单>.md`
  - 契约 `board/contract-p1.md`
  - 设计 `doc/agent-cluster-design.md`

## 做法
1. **准备被审代码**：在你自己的 worktree `/home/ubuntu/Projects/easygo-acl-review` 里 `git checkout --detach <sha>`，或者 `git archive` 到 `/tmp/crew/acl-530e/review/<sha 前 7 位>/`。复现代码只放在这些地方。
2. **只认自己取的证**：
   - 自己跑测试、自己在专用 daemon 上起真实容器；
   - 构造恶意或边界输入；
   - 必要时故意做坏一个变体，证明测试能判红。

   施工者报审里的数字只作为线索，不作为结论。
3. **重点审查**：
   - 契约一致性；
   - 安全边界：施工者能否冒充、能否改检查、检查容器能否联网或拿到凭证、路径逃逸；
   - 状态机：取消、重启、竞态；
   - 幂等与不重不漏；
   - 资源上限：消息条数、输出大小；
   - 测试是否真的测到了它声称的东西。
4. **分级**：
   - P0：安全或数据错误；
   - P1：违反契约或验收标准；
   - P2：稳健性问题；
   - P3：建议。

   每条都要写：复现步骤、证据路径、涉及的文件和行号。

## 明令不做
- 不改施工者的分支，不修代码，不 push。
- 不联系施工者，所有结论只交给工头。
- 不调用付费模型，不读 key。
- 资源纪律同 brief：真实容器测试用最小配额，测完清理。

## 交付
- 每次审查写一份 `board/review-<单>-<sha7>.md`，按以下顺序：
  1. 结论：通过 / 有条件通过 / 不通过；
  2. 问题列表，按 P0–P3；
  3. 已验证无问题的项（附证据）；
  4. 没覆盖到的范围。
- 然后 herdr-msg 通知工头，附 delivery_id。
